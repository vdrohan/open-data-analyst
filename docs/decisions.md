# Decisions

Format: number, date, decision, reasoning.

1. 2026-10-16 - Project is an open-data analyst agent, not a server-ops agent or workflow tool. Extends the earlier support-desk project (answers from documents) to agents, tool use and structured data.
2. 2026-10-16 - Theme is Canadian housing (starts, rents, prices), chosen over labour market + CPI, federal spending and demographics. Relevant to a rent-versus-buy decision in Metro Vancouver, and the owner is the "client" asking the questions. Trade-off: housing data comes from several sources with inconsistent geography codes, so Phase 1 is slower.
3. 2026-10-16 - Client is the owner (as in the earlier support-desk project). Revisit adding an outside client after Phase 3 if one is available.
4. 2026-10-16 - DuckDB as the store (no server process, light on RAM on a modest laptop). Postgres only if a later need appears.
5. 2026-10-16 - Cloud-only AI; Claude Haiku for the agent loop by default, with a step cap and per-question cost logging.
6. 2026-10-16 - Repo stays private until the eval set exists (Phase 2).
7. 2026-10-16 - Question focus is monthly cost: rent versus mortgage payment on a new property. Mortgage payment will be a calculator tool (Canadian semi-annual compounding), not a table lookup, so answers stay exactly checkable. Source survey in the project files (phase1-source-survey.md); assumptions for down payment and amortization still to be set.
8. 2026-10-16 - Scope is every municipality within 40 km of downtown Vancouver and all dwelling types (house, condo, apartment, townhouse). The owner chose a distance rule over commute time, so membership is computed, not judged: a reference table of municipalities with centroid coordinates, straight-line distance from a fixed downtown point (Waterfront Station, about 49.2858 N, 123.1117 W), and an in-scope flag. Straight-line, not road distance; the choice is stated in answers. Where a source only reports the Vancouver CMA or lacks a dwelling type, the agent must say so rather than infer.
9. 2026-10-16 - Calculator defaults confirmed by the owner: 20% down, 25-year amortization, as parameters. Not financial advice; insured-mortgage rules to be checked.
10. 2026-10-16 - Bank of Canada series V122521 (named in the Phase 1 survey) was discontinued after 2019-09-01. Both it and the weekly successor V80691335 ("Conventional mortgage, 5-year", latest 6.19% on 2026-10-14) are loaded and labelled; the agent must use V80691335 for any current rate. Both are posted rates, not the rate a buyer is offered.
11. 2026-10-16 - CMHC absorbed units are loaded from the CMA workbooks only: full years 2016-2025 plus single months of 2026 (Jan-Aug). CMHC also publishes every month and quarter; loading all would count each sale up to three times, so months are used only for years without a full-year file. The CMA workbooks list census subdivisions (municipalities) for every year, including 2023-2026, which the survey feared would be CMA-only. CA (smaller centre) workbooks are skipped: they end in 2022 and are far from Vancouver.
12. 2026-10-16 - Municipality reference point is the named city/town/village centre from Natural Resources Canada place names (CGNS), not the centroid of the legal boundary, because a boundary centroid would drop large mostly empty districts (Maple Ridge) that are mostly populated near Vancouver. District municipalities use CGNS's district record; Electoral Area A uses the UBC campus. Distances within 3 km of 40 km are flagged `borderline`. The StatCan boundary files (www12.statcan.gc.ca) are blocked in the build environment, which is why boundary centroids were not used. Trade-off: reference points are a judgement; the rule and each point's source are stored in the table.
13. 2026-10-16 - The store is rebuilt from scratch from `data/raw/` on every build (no incremental updates) and every table and column carries a description written as a DuckDB comment; `docs/data-dictionary.md` is generated from the same source and a test keeps it current.
14. 2026-10-16 - Owner's real question profile, from the owner: a 1-bedroom condo, Surrey, Burnaby and Vancouver, with $2,500 rent and 20% down as working defaults (the owner accepted the defaults; the amounts are placeholders to correct later). The eval set is built around this profile. Limit found while building it: CMHC new-home sales are not split by bedroom count and rents exist only for the whole Vancouver metro area, so "1-bedroom condo price in Surrey" and "cheapest city to rent in" are refusal cases, not answerable ones.
15. 2026-10-16 - Eval format: one JSON line per question with an exact expected answer, tolerance, and the SQL (plus mortgage inputs) that produced it, so `evals verify` re-derives every expected number after a data refresh instead of trusting stored constants. Scoring separates wrong answers and overreach (answering something the data cannot support) from missed answers, because a confident wrong number is the worst failure. A correct value without a shown query does not pass. The always-abstain floor scores 29% (12 of 41) with zero confident-wrong answers; a real agent has to beat it on accuracy without adding confident-wrong answers.
16. 2026-10-16 - Agent loop is a hand-written Claude tool-use loop over the Anthropic SDK (`messages.create`), not the SDK's tool runner or a framework. Options: tool runner (less code, but the step cap, per-question cost log, query check and budget cap would have to be bolted on through hooks), an agent framework (extra dependency, hides the loop a reviewer wants to read), hand-written loop (about 100 lines, every guardrail visible). Chose the hand-written loop. The model client is injected, so tests use a scripted fake and cost nothing.
17. 2026-10-16 - SQL guardrails are three independent layers: the DuckDB connection is opened read-only, file and network access is disabled with the configuration locked, and only a single statement of type SELECT is accepted; results are capped at 50 rows and a query is interrupted after 10 seconds. The agent can never write to the store even if one layer is wrong. Trade-off: the 50-row cap means "list everything" questions get a truncated answer, which the tool says explicitly.
18. 2026-10-16 - The agent ends with one of two tools, `submit_answer(value, query, explanation)` or `abstain(reason)`, instead of free text, so answers are structured and scoring needs no text parsing. `submit_answer` is bounced back to the model unless its `query` is one that actually ran, which enforces "every answer shows its query". Running out of steps, a refusal from the model, or ending without a final tool all count as abstaining, never as a guess.
19. 2026-10-16 - Agent model is Claude Haiku 5.5 (`claude-haiku-5-5`, $0.10 in / $0.50 out per million tokens) with a 10-step cap and a spend cap per eval run (default $1), per rule 4. Thinking is left at the model default. If Haiku misses answerable questions, the next step is a Sonnet run on the same set to separate model limits from prompt or schema problems, before changing the prompt.
20. 2026-10-19 - First live run scored 37%, but 22 of 25 wrong answers were correct numbers sent as text because the `submit_answer` value schema accepts a string. Options: loosen the scorer to accept numeric text (hides the defect and weakens "exact answers"), tighten the schema to number-only (breaks place-name and true/false answers, which share the field), or convert in the agent loop. Chose to convert a finite numeric string to a number in the loop and keep the scorer strict, so the answer handed to callers is typed correctly. Also bounce a `submit_answer` whose value is a decline word ('abstain', 'n/a') back to the `abstain` tool, since a decline sent as a value counts as a confident answer. Trade-off: the loop now silently normalises numeric text, so a question whose true answer is a numeric-looking string would be mis-typed; none exists in the set.
21. 2026-10-20 - Two questions failed in every run. Scope-count: the agent excluded the in-scope electoral area because the question said "municipalities" and the table labels it `electoral_area`. Options: change the agent to count it (wrong, the agent read the table correctly), change the expected answer to 22 (loses the electoral area the owner's scope rule includes), or reword the question to name both. Chose to reword, since the question was ambiguous, not the agent. Compare-vancouver: the agent used the metro-wide price because "Vancouver metro" appeared in the same sentence. Chose a prompt rule (a bare city name means the city, a metro figure is used only when labelled metro, CMA or region), leaving the question unchanged so the agent fix is what gets tested. Risk: editing an eval question after seeing the agent fail on it can flatter the score; the change and its reason are recorded here, and fresh unseen questions are the next check.
22. 2026-10-20 - Housekeeping before Phase 4: Phase 3 closed in the impact log, README rewritten for outside readers (results table, example answers, architecture, limits), personal details removed from the docs, and a data licence and attribution section added after reading each publisher's terms. The owner approved going public once the repo is ready. The holdout gate is met (91% on 22 unseen questions, in the README). Options were: go public now (README makes claims the holdout has not tested), after the holdout (chosen), or stay private (no outside value).
23. 2026-10-20 - Holdout check before more features. Options: owner writes the questions (most realistic wording, costs the owner time), I write them for the owner to review (chosen), reuse the tuned set (proves nothing). The holdout is `data/eval/holdout.jsonl`, derived by SQL like the main set; the agent and prompt are not changed to fit it. Its first score is reported as is. If it exposes misses, fixes are made and the set is then retired from the unseen role, with the new unseen score reported separately. Trade-off: I wrote the questions after reading the tuned set, so they are unseen by the agent but not independent of how I think questions should look; the owner's review is the check on that.
24. 2026-10-20 - Model rule, confirmed by the owner. Pay-per-token API calls (the project's agent and all eval runs) use Haiku only: no Sonnet comparison run, which supersedes the fallback in decision 19, and if Haiku misses questions the levers are prompt, tool descriptions and table descriptions, not a bigger model. Work covered by the owner's Pro subscription (the coding session and any sub-agents it starts) uses Sonnet; Opus and Fable are not used.
25. 2026-10-20 - Fixes for the two holdout misses, prompt-level only. Yes/no: options were a code-level coercion of "yes"/"no" strings (cannot know the question was yes/no, and the failure was a number, not a string), a stricter schema (booleans share the `value` field with numbers and text), or a prompt and tool-description rule that yes/no questions get true or false (chosen). Metro-only figures: options were leaving it (honest refusal, but a missed answer for "Toronto rent"), a rule that a metro figure may stand in for a city named after it, labelled metro-wide (chosen), or answering any place with its metro's figure (rejected: that is the substitution rule 2 forbids, and Surrey rent must still be refused). A first wording that told the agent to decline for any place inside the metro made a legitimate rent-versus-buy comparison refuse in 2 of 3 runs, so it was reworded. Trade-off: the holdout is no longer unseen after this; the README keeps the first, untuned 91% as the quoted figure and shows the post-fix 100% separately. Open risk: a refusal explained in the text but sent through `submit_answer` showed up once in three runs; a loop-level check is the next candidate.
