# Impact log

One entry per phase: what was built, how it was measured, and what the result was.

## Phase 0 - Scope and scaffold
- Scoped a natural-language analyst agent over Canadian housing data; chose stack and guardrails; set up CI, linting, secret scanning and a decisions log.
- Metrics: none yet.

## Phase 1 - Data layer and calculation tools
- Built and tested the mortgage payment function (Canadian semi-annual compounding, validated by amortizing the loan to zero and against a known figure: $500,000 at 5% over 25 years is $2,908.02 a month) and the distance function that defines the 40 km scope.
- Built a repeatable ingest from three Canadian public sources into a DuckDB store: Bank of Canada posted 5-year mortgage rate (3,264 observations, 1973 to Oct 2026), Statistics Canada quarterly asking and paid rent by metropolitan area (9,646 rows, 2019 to Apr 2026), and CMHC new-home sales by price band and municipality (806,887 rows, 2016 to Aug 2026) parsed from 18 Excel workbooks, plus a 31-row municipality table that flags the municipalities within 40 km of downtown Vancouver (23 in scope, 4 of them borderline). One command refreshes everything.
- Found and documented source problems before they reached answers: the Bank of Canada series named in the plan stopped updating in 2019 (replaced with its weekly successor), CMHC publishes overlapping month, quarter and year files that would triple-count sales, and CMHC suppresses small counts. Cross-checks: band counts reconcile to published row totals except where cells are suppressed (29,027 rows match, 5,489 differ and every one contains a suppressed cell).
- Every table and column has a description stored in the database and rendered to docs/data-dictionary.md; a test fails if they drift apart.
- Metrics: 27 unit tests passing (parsers, scope rule, store build, dictionary currency).

## Phase 2 - Eval set
- Built the eval harness before any agent code: a question format with exact, tolerance-checked expected answers, a scorer that separates correct answers, correct refusals, missed answers, wrong answers and overreach (answering what the data cannot support), and a verifier that re-derives every expected number from the data after a refresh.
- Wrote 41 questions (12 lookups, 12 calculations, 5 scope checks, 12 refusal cases), built around the owner's real use (renting vs buying a 1-bedroom condo in Surrey, Burnaby or Vancouver) and including the owner's own five questions on rent vs buy, cheapest city to rent or buy, and rent per city. All 29 answerable expected values were derived by SQL and mortgage maths, not typed in.
- Baseline: an agent that always refuses scores 29% (12 of 41) with 0 confident-wrong answers; this is the floor a real agent must beat.
- Metrics: 35 unit tests passing. Question set is at the 40 to 60 target's lower edge; more of the owner's own wording is welcome.

## Phase 3 - Agent core
- Built a Claude tool-use agent that answers housing questions by reading the table descriptions, writing SQL, running it, and calling a tested mortgage calculator, then returns a structured answer with its query or refuses with a reason. Default model is Claude Haiku 5.5 with a 10-step cap, a per-run spend cap, and tokens and dollars logged for every question.
- Guardrails: read-only database connection, file and network access disabled and locked, single-SELECT validation, 50-row and 10-second limits; an answer whose cited query was never run is rejected; running out of steps or model refusals become abstentions. Tested with a scripted fake model (14 tests: write attempts, file access, row limit, timeout, query-citation check, step cap, budget cap, eval-runner integration), so the logic is verified without spending anything.
- Metrics: 49 unit tests passing.
- First live run (2026-10-19, Claude Haiku 5.5, 41 questions): 37% accuracy (4 correct answers, 11 correct refusals) against the 29% always-abstain floor, with 26 confident-wrong results (25 wrong, 1 overreach). Cost $0.096 for the whole run, $0.0023 per question, 3.6 steps per question on average (760K input and 40K output tokens). Refusal behaviour was strong: 11 of 12 unanswerable questions correctly refused.
- Diagnosis from the run's traces: 22 of the 25 wrong answers were correct numbers returned as text (for example '6.19' for 6.19), which the scorer counts as wrong because the `submit_answer` value schema allows a string. Treating those as correct would put accuracy at about 90% (37 of 41); that is an estimate from the traces, not a scored run. The 3 real mistakes were a count that left out the electoral area (22 instead of 23), a comparison built on the metro-wide price instead of the City of Vancouver, and a city name returned with extra text. The one overreach was a refusal sent through `submit_answer` as the value 'abstain' instead of the `abstain` tool.
- Fix and re-run (same day, same model and set): numeric text from the model is converted to a number in the agent loop, a `submit_answer` whose value is a decline word such as 'abstain' is bounced back to use the `abstain` tool, and the prompt asks for bare place names. Result: 95% accuracy (27 correct answers, 12 of 12 unanswerable questions correctly refused, 39 of 41), 2 confident-wrong answers and no overreach, up from 26 confident-wrong in the first run, for $0.087 total, $0.0021 per question, 3.5 steps per question. By category: lookups 12/12, refusals 12/12, calculations 11/12, scope 4/5. The first-run estimate of about 90% from the traces understated the result because the place-name and 'abstain' fixes also landed.
- Remaining misses, both reasoning errors rather than format problems: the scope count excluded the one electoral area that the table flags in scope (22 instead of 23), and one rent-versus-buy comparison used the metro-wide apartment price instead of the City of Vancouver's. Both are candidates for a table-description or prompt tweak, or a Sonnet comparison run (decision 19).
- Lesson for the write-up: a strict scorer exposed a tool-schema weakness that would have shipped as a silent "answers are strings" bug; the fix was one conversion plus two tests (51 unit tests now).
- Repeatability check (3 full runs, same model and set, before the next fixes): 90%, 95% and 95%, about $0.09 per run and 3.5 steps per question. 37 of 41 questions passed every run; two failed every run (the scope count and a Vancouver rent-versus-buy comparison) and two were flaky (one place-name format slip, one needless refusal). A single run's score therefore moves by about 2 questions (5 points).
- Fixes for the two consistent failures: the scope-count question was ambiguous and the agent's answer (22) was literally correct, because the table itself labels the one in-scope electoral area as not a municipality, so the question now says "municipalities and electoral areas" (expected answer unchanged at 23); the agent now reads a bare city name as the city rather than the metro area. Result: 3 of 3 runs scored 100% (41 of 41, 0 confident-wrong), $0.088 to $0.094 per run, about $0.0022 per question. One of the two fixes changed the question rather than the agent, so the honest claim is "100% on the revised set, 3 runs", with the earlier 90 to 95% on the original wording.
- Limits of this result: the set has 41 questions and was tuned against its own failures, so 100% here is not a forecast for new questions. Next step is fresh questions the agent has never been tuned on.
- Holdout check (2026-10-20): 22 new questions (16 answerable, 6 unanswerable), written after the agent was tuned, with expected values derived by SQL and none of them used to change the agent. One run on Claude Haiku 5.5 scored 91% (20 of 22) for $0.045, with 6 of 6 unanswerable questions correctly refused, scope 3/3, lookups 5/6 and calculations 6/7. Against 100% on the tuned set, the 9-point drop is the measured cost of tuning on the original questions. One question is worth about 4.5 points, so the gap and the score are both rough.
- Miss 1 (wrong): asked whether a Burnaby condo payment is higher than Vancouver paid rent, the agent computed everything correctly (about $4,714 a month against $1,890) and wrote "Yes" in its explanation, but put the payment number in the answer value instead of a yes/no. The same kind of weakness as the first run's string-versus-number problem: the answer-value field is untyped and the model uses it inconsistently for yes/no questions.
- Miss 2 (missed answer): asked for Toronto asking rent, the agent refused because the data covers the Toronto metro area, not the city. That is the "a bare city name means the city" prompt rule from the tuned set carrying over to a place where only the metro figure exists, and arguably the question is ambiguous. The refusal was honest and offered the metro figure, but it counts as a missed answer.
- Fixes for the two holdout misses (prompt and tool-description only, no model change): a yes/no question must be answered with true or false and the numbers go in the explanation; and where a table reports only a metro area named after its main city (Toronto, Vancouver), the agent answers with the metro figure and labels it metro-wide, while never presenting it as the rent of a place inside the metro (Surrey, Burnaby).
- Results after the fixes: the 22 holdout questions scored 100% on re-run (twice, with two wordings of the metro rule), and the 41 tuned questions scored 98%, 100% and 100% over three runs with the final wording. A first wording of the metro rule ("decline" for any place inside the metro) made a Surrey rent-versus-mortgage comparison refuse in 2 of 3 runs, so it was loosened; that wording trial is included in the spend. The 98% run had one confident-wrong answer: for Squamish rent the agent wrote an explanation saying the data had no Squamish figure, then sent it through `submit_answer` instead of `abstain` (it refused correctly in the other two runs). That is the same intermittent failure shape as the first live run and is a candidate for a loop-level guard.
- How to quote this: 91% on the unseen holdout is the honest figure. The 100% re-runs are on questions the fixes were designed from, so they show the fixes work, not that accuracy is now 100% on new questions. Spend for all of today's runs, including the first holdout and the wording trials, was about $0.70.

## Phase 4 - Charts and MCP server (in progress)
- Wrapped the housing tools as an MCP server (stdio) with five tools: `describe_schema`, `run_sql`, `mortgage_payment`, `make_chart` and `ask`. The four primitives let a client such as Claude Desktop do the reasoning at no API cost; every query still goes through the read-only store with its 50-row and 10-second limits. `ask` runs the project's own evaluated Haiku agent and is the only tool that spends money, capped at $0.25 per server session.
- Added chart output as a Vega-Lite spec (bar or line, up to 50 points, numeric y) with the data embedded, so the same output can later feed the web UI.
- Verified two ways: 9 new unit tests (60 in all) cover every tool, write attempts, bad chart input, `ask` with a scripted fake model including abstention, failure and budget cap, with no network or spend; and a real MCP client over stdio listed the five tools, produced a Surrey new-condo sales chart from the live store (1,306 units in 2017 to 4,798 in 2025) and had a `DROP TABLE` refused with the reason shown.
- Found and fixed before release: the SDK hides messages from plain exceptions, so tool errors would have reached the client as a bare "Error executing tool"; errors now use `ToolError` and a test covers it.
- Not yet verified: the server inside the Claude Desktop app itself (config snippet is in the README) and the `ask` tool against the live API.
